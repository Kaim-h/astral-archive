## Checkpoint N1a — proposed model and compatibility

- Keep Core's single validated snapshot, revision, file-owner enumeration, Case and 30-entry Undo. The historical `cubbies` dictionary and `cubbyId` locator names now serve as compatibility names for physical containers in the opt-in spatial envelope. Explicit `spatial.shelves[containerId]` identifies architectural Shelf roots, not hidden Cubby wrappers. Other physical containers are nested Cubbies; one owner path to a Shelf, no cycles or nested architectural Shelf roots. Room map rectangles have stable IDs; architectural Shelf placement references its Room. Room/Shelf/fixture/cell structural identities must not collide in spatial state. File IDs remain distinct logical identities.
- Rectangular integer model units retain native B6/B7 scale. A Shelf's usable interior width/height are existing container w/h; its exterior width/height derive from the same border b on both sides (default 11). Room footprint width derives from exterior width, and independent plan depth; cardinal orientation swaps axes. Room footprint anchor is its local top-left bounding corner. Room movement retains local Shelf coordinates; height changes do not change plan footprint; invalid shrink or overlapping placement refuses atomically. This is an initial conservative engineering contract, not accepted final cornice/overhang or depth clearances. Room bounds 130–10000 by 100–10000, map origin ±100000, depth 40–1800, max 64 Rooms, combined 128 physical containers; other inherited budgets unchanged.
- Structural commands use Core.previewStructure/applyStructure and same-ID validation. Creating/moving/resizing Rooms and Shelves, nested fixtures, explicit family/palette references, and occupied Shelf removal are supported at model level. Shelf deletion reuses existing recursive fixture evacuation on unpublished values, then commits once; stale origins and prior Case entries retained. Last Shelf and last Room protected; Room removal requires separately resolving its Shelves. Family inherits nearest explicit ancestor (including None); palette is local to the current container, otherwise desktop theme. Catalogue key validation/visual interpretation and room-specific palette rendering remain later work.
- Legacy v1/v2 checkpoints decode unchanged; legacy writer still v2. An explicit, undoable synthetic `spatialPromote` operation reinterprets the existing study root as the initial architectural Shelf in Main Hall, retains its ID, fixtures, file ownership, dimensions, cameras and path. No implicit migration on load or user-file rewrite; this promotion is a proposed compatibility path, not a mandate to promote existing Cubby study saves. Version 3 only for spatial snapshots; old format cannot disguise spatial state. Frontal physical path starts at an actual Shelf root; Map/Room navigation and cameras are not yet represented. Legacy study controllers reject v3 unless explicitly opted in; opt-in currently for foundation tests, not new user-facing UI.
- Boards retain existing explicit local object/holder placements, asset anchors, occupied envelopes and file owner locators; racks retain existing live motion and reflow; no new flat-top support solver, app placement or door graph in N1a. These are next bounded N1 model questions, not claimed complete. Add generalized support references/eligibility, app identity/placement and shared edge/door schema after review; complete bounded-capacity and migration review before N1 acceptance. The initial tests exercise a populated mixed v2/v3 checkpoint, movement of a board with unchanged local dependent coordinates, nested evacuation with pre-existing Case entries and active path rollback. Unified appearance/geometry Undo UI and navigation remain later milestones.

## Checkpoint N1b — explicit physical support

A horizontal board remains intrinsically eligible. In spatial v3 only, a rack or nested Cubby module may explicitly declare `flatTop:true` via `spatialSupport`; no assumption that every decorative/profile variant is suitable. The provisional horizontal contact datum is the module's outer top (x, y, w), not the child interior. Supported entries retain the B7 local x, scale, contact anchor, preferred metadata and reserved holder/cradle envelopes. The existing `items` array belongs directly to the supporting module; there is no generated board, additional record inventory, duplicated ownership, arbitrary stacking graph or support cycle. A rack may simultaneously own cell scrolls and supported file objects. Existing B7 owner locators (where=shelf/holder, moduleId) retain compatibility; this describes physical support, not a folder. Board/rack/Cubby movement carries local entries without scaling. Width shrink, ceiling/side overlap, collision with other fixtures or reserved cradles refuses using the same occupied envelopes; rack reflow remains unchanged. Disabling a surface requires resolving all dependent objects/holders first; deletion uses existing Case evacuation and exact Undo for cells, direct top objects and descendants. A lost/invalid Case origin refuses return rather than moving other contents. New top items consume the same fixture/record budgets; legacy formats cannot carry them. This is a conservative flat frontal contact model, not a load-bearing simulation or a finalized depth/ornamental profile clearance contract. Native top rendering, hit targets and pointer movement belong to N2; the actual shared motion transaction and pure model are exercised now. Application books remain separate N1c work, not synthesized as file entries. No source assets or legacy study visuals replaced.
